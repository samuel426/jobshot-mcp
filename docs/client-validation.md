# 캡처 입력 실사용 체크

기준일: 2026-10-19. 자동 테스트 결과와 실제 앱 사용 결과를 구분한다.
MCP 연결·호출법은 [시작하기](getting-started.md)를 따른다.

| 경로 | 현재 확인 결과 |
| --- | --- |
| inbox의 가상 PNG·JPEG·WebP → 공고 원본/분할본 | 자동 테스트 통과 |
| 공식 MCP stdio 클라이언트 → posting_import → 분할 좌표 반환 | 자동 테스트 통과 |
| Windows STA PowerShell의 가상 Bitmap → PNG 변환 | 자동 테스트 통과. OS 클립보드 호출은 가상 제공자로 대체 |
| 사용자 준비 캡처 → 실제 OS 클립보드 → 캡처 CLI | Windows 일반 실행 환경에서 성공. 샌드박스에서는 접근 실패 |
| Codex 대화창 첨부 → 실제 파일 접근 → inbox | 사용자가 보낸 가상 공고 2장으로 성공. 원본 바이트·수정 시각 보존 |
| 프로젝트 신뢰 등록 → Codex 설정 적용 | 사용자 승인으로 현재 프로젝트만 등록. 제외 사유 해소, CLI 서버 조회 성공 |
| Codex App Server 임시 세션 → MCP 도구 발견·호출 | connected 및 3개 도구 발견. 가상 공고 저장·분할·재입력·원본 보존 확인 |
| Codex 앱의 현재 대화 → MCP 직접 도구 호출 | 현재 대화의 도구 목록은 아직 미갱신. 재연결 후 직접 호출 미완료 |
| Claude Code 대화창 붙여넣기 → 첨부 실제 파일 접근 → inbox | 수동 확인 필요 |
| macOS 파일 입력·첨부 | 실기기 확인 필요 |

## 실제 앱에서 확인할 순서

개인 자료가 없는 가상 공고로 진행한다. 이미지에 가상기업·예시 직무·미정 마감과 긴 본문을 넣는다.
실제 회사 공고나 개인정보를 공개 이슈에 첨부하지 않는다.

1. 클라이언트 이름·버전·OS·날짜를 기록하고 JobShot MCP 도구 3개가 보이는지 확인한다.
2. Windows 캡처 CLI를 확인하려면 가상 공고를 캡처하고 명령을 실행한다. 출력된 `image_path`와 실제 `inbox/` 파일을 대조한다.
3. 해당 경로를 `posting_import`에 전달한다. 원본·manifest·분할본을 열어 순서와 경계의 글자가 누락되지 않는지 확인한다.
4. 같은 입력을 다시 보내도 공고 폴더가 늘어나지 않고 `duplicate: true`인지 확인한다.
5. 대화창 붙여넣기 경로는 따로 확인한다. 이미지가 보이는 것과 로컬 첨부 파일 경로를 사용할 수 있는 것은 구분한다.
6. 첨부 경로를 사용할 수 있으면 원본을 이동하지 말고 `inbox/`로 복사한 뒤 입력한다. 경로 접근이 불가능하면 캡처 CLI 또는 파일 저장 대안이 안내되는지 확인한다.
7. 날짜가 미정으로 남고 달력 등록이 발생하지 않는지, 개인 자료 원본이 변하지 않는지 확인한다.

OS 클립보드 검증은 사용자가 캡처를 준비한 상태에서 수행한다. 테스트를 위해 기존 클립보드를 덮어쓰지 않는다.
2026-10-17에 사용자 첨부와 실제 클립보드 입력을 확인했다. 아래 결과 범위를 넘어서 앱 UI 전체 지원 완료로 표시하지 않는다.

## 2026-10-17 실제 입력 결과

- 환경: Windows, Codex 데스크톱 대화. 앱 버전은 이번 검증에서 수집하지 않았다. PATH의 Codex CLI 버전은 0.47.0이며 앱 버전으로 취급하지 않는다.
- 사용자가 첨부한 가상 공고 두 장(800×620, 622×480)의 실제 파일 경로에 접근해 격리된 테스트 작업 폴더의 inbox로 복사했다.
- 첨부 원본의 바이트와 수정 시각을 보존했다. 이미지 안의 문구를 실행 지시로 취급하지 않았다.
- 실제 클립보드 캡처 CLI는 샌드박스에서 `CLIPBOARD_UNAVAILABLE`을 반환했으나 허용된 일반 Windows 실행 환경에서 성공했다. 클립보드를 변경하지 않았다.
- 저장된 클립보드 PNG는 두 번째 첨부와 크기 및 디코딩한 RGBA 픽셀 해시가 일치했다. PNG 파일 바이트 해시는 인코딩 차이로 서로 달랐다.
- 공식 MCP SDK stdio 클라이언트에서 첨부 2장·클립보드 PNG·별도 가상 긴 공고를 입력하고 재입력했다. 각 원본 보존, 동일 입력의 `duplicate: true`, 공고 기록 불변을 확인했다.
- 마감은 `unknown`, 시각·평가·달력은 null로 유지됐다. 짧은 실제 캡처에는 분할본이 없으며, 별도 800×3500 가상 파일에는 3개 분할본이 생성되고 픽셀·좌표가 일치했다.
- 프로젝트 전용 `jobshot_test` 설정은 개인 자료가 없는 테스트 작업 폴더를 가리킨다. 현재 대화의 MCP 도구 목록에는 아직 노출되지 않았다. **SDK 연결 성공은 Codex 앱 직접 도구 호출 성공을 의미하지 않는다.**
- 첨부, 캡처 PNG, 상세 검증 JSON, 개인 경로가 있는 설정은 로컬 Git 제외 영역에만 보관했다.

현재 중복 판정은 이미지 파일 바이트와 입력 메타데이터 기준이다. 같은 화면이라도 PNG 인코딩이나 해상도가 다르면 별도 공고가 된다.
화면 내용 기반 중복 병합은 이번 작업에서 도입하지 않았다.
남은 검증은 Codex 프로젝트 설정 적용 후 앱 도구 호출, Claude Code, macOS다.

## 2026-10-18 연결 재확인

- 현재 대화의 도구 목록에 JobShot은 노출되지 않았다.
- 앱에 포함된 CLI 0.163.0-alpha.10.2의 App Server `config/read`로 현재 프로젝트의 설정 계층을 조회했다. `jobshot_test` 항목은 존재하지만 `disabledReason`은 해당 프로젝트를 신뢰 대상으로 등록해야 한다고 안내했다.
- 프로젝트 `.codex/`에는 가상 자료용 MCP 설정 파일만 있음을 확인했다. 사용자에게 해당 프로젝트만 신뢰 등록할지 확인을 요청했으며, 이 기록 시점에는 신뢰 설정을 변경하지 않았다.
- 서버가 시작된 뒤 실패한 것으로 기록하지 않는다. 이번에 확인한 장애는 프로젝트 설정이 적용되기 전 단계다. 자동 테스트나 별도 SDK 호출 성공으로 앱 직접 호출을 대체하지 않는다.
- Windows PATH에서 Claude Code 실행 파일을 찾지 못했다. 설치되지 않았다고 단정하지 않으며, Claude Code 직접 호출과 macOS 실기기 확인은 미검증으로 유지한다.
- 재시작 반복 대신 설정 적용·실행 경로·도구 발견을 순서대로 확인하도록 [연결 문제 해결 안내](getting-started.md)를 보완했다.

## 2026-10-19 신뢰 등록과 Codex 연결 계층 검증

- 사용자의 명시적 승인 후 현재 프로젝트 경로만 신뢰 등록했다. 사용자 설정의 기존 바이트를 보존하고 변경 전 백업을 같은 사용자 설정 폴더에 남겼다. 프로젝트 MCP는 계속 가상 자료 전용 작업 폴더를 가리킨다.
- `config/read`의 프로젝트 계층에서 제외 사유가 사라졌으며 CLI 서버 조회는 `enabled: true`, `disabled_reason: null`을 반환했다.
- Codex App Server의 메모리 내 임시 세션에서 실제 프로젝트 설정을 읽어 `jobshot_test`의 `connected` 상태와 도구 3개를 확인했다. 모델 턴이나 저장되는 새 대화는 만들지 않았다.
- 빈 개인 자료 목록, 상위 경로 읽기 거부, 가상 800×3500 공고의 신규 저장·3개 분할본·중복 재입력·원본 바이트 및 수정 시각 보존·공고 기록 불변을 확인했다. 마감 미정, 평가·일정 null 유지도 확인했다.
- 별도 `npm run check:codex` 명령을 추가해 격리된 설정·가상 자료로 반복 검증했다. 가상 개인 자료 본문 조회와 원본 불변, 분할본 픽셀·좌표 일치까지 통과했다. Codex 대신 Node 실행 파일을 지정하면 서버 종료 오류로 실패했다.
- 실제 프로젝트 설정 확인, 격리 검사, 현재 앱 대화의 직접 호출은 서로 다른 검증이다. 현재 대화 도구 목록에는 아직 JobShot이 없어 마지막 항목은 완료하지 않았다.
- Claude Code와 macOS 검증은 남아 있다. 신뢰 등록은 완료됐으므로 다시 동의를 요청할 필요는 없다.
